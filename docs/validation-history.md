# 검증 기록 (README에서 옮긴 예전 비교)

README가 지금 파이프라인 위주로 바뀌면서, 그 전에 README에 있던 비교 기록을 그대로 옮겨 둡니다. 숫자는 그때의 코드와 보정으로 잰 값입니다.

## 예전 1분 비교: `detection/` 대 우리 검출 (2026-11-10 무렵)

11/17 정답 클립 비교 전에 파이프라인이 `detection/`(차재혁)을 쓰던 때의 기록입니다. 10/8 영상 10:00부터 1분. 숫자는 앞이 `detection/`, 뒤가 우리 검출입니다. 박스는 같은 프레임에 우리 검출(YOLO26x, conf 0.1)을 다시 돌려 비교했습니다.

- **conf 0.3** (우리는 0.1): 박스가 프레임당 cam1 10.7개 대 12.2개, cam2 12.6개 대 14.6개로 약 13% 적습니다. 빠진 것은 대부분 신뢰도 0.1~0.3 박스이고, 대부분 코트 밖입니다. 코트 안(발이 코트에서 1 m 이내) 박스만 세면 cam1 7.9개 대 8.2개, cam2 8.5개 대 8.8개로 약 4% 적습니다 (코트 안 숫자는 저장된 `cache_full26` 박스로 셈). 신뢰도 0.3 이상인 우리 박스 중 ByteTrack이 내지 않은 것(아직 확정 안 된 트랙)은 1.0%(cam1), 1.5%(cam2)입니다.
- **ByteTrack 박스**: 칼만 필터로 다듬은 위치지만 차이는 작습니다. detection/ 박스는 99.9% 이상 우리 박스와 겹치고(IoU 0.5 이상), 발 위치 차이는 중앙값 0.2 px(90%가 1.1 px 이내), 코트 위로 중앙값 0.01 m(90%가 0.08 m 이내)입니다.
- **추적 결과** (같은 1분, 같은 `calibration/` 좌표. 우리 쪽은 다시 돌린 박스가 아니라 저장된 `cache_full26` 박스라서 cam1 프레임이 한 장(16.7 ms) 어긋납니다): `detection/` 박스는 ID 11개, 절반 넘게 보인 ID 10개, 한가운데서 생기거나 끊긴 ID 1건, 두 카메라 위치 차(정렬 후) 0.148 m, 절반 넘게 보인 10명의 이동거리 합 751 m. 우리 박스는 ID 12개, 10개, 4건, 0.148 m, 780 m. 정답 위치가 없어서 어느 쪽이 맞는지는 모릅니다. 1분 한 구간만 봤습니다.
- 같은 검출 결과로 다시 돌리면 추적 결과도 같습니다. 처음 돌릴 때도 저장된 검출 결과(ReID 특징은 float16)를 다시 읽어서 추적하기 때문입니다. 예전에는 처음 돌릴 때만 float32 특징을 써서, 20:00부터 3분 구간에서 처음 결과(절반 넘게 보인 ID 10개, 사건 3건)와 다시 돌린 결과(9개, 4건)가 달랐습니다. 반올림 정도의 차이로도 결과가 바뀌니, 짧은 구간 하나의 비교는 조심해서 봐야 합니다.
- 추적 v2의 설정과 [추적 v2](tracking-v2.md)의 숫자는 우리 검출(conf 0.1)과 우리 탭 보정으로 맞추고 잰 값입니다.

## 보정 비교: 우리 탭 보정 대 HOGEUN 예전 한 장면 보정 (11/11 이전)

53분, 같은 검출 `cache_full26`, 같은 추적. `calibration/` 열은 HOGEUN의 예전 한 장면 보정입니다.

| | 우리 탭 보정 (`calib/`) | 우리 탭 보정 + 새로 잰 카메라 움직임 | `calibration/` (HOGEUN) |
|---|---|---|---|
| ID 수 | 32 | 29 | 26 |
| 경기 절반 넘게 보인 ID / 80% 넘게 보인 ID | 6 / 5 | 7 / 6 | 7 / 4 |
| 한가운데서 생기거나 끊긴 ID | 33번 (분당 0.62) | 27번 (분당 0.51) | 21번 (분당 0.40) |
| 두 카메라 위치 차 (정렬 전 → 후) | 0.647 → 0.207 m | 0.664 → 0.209 m | 0.684 → 0.210 m |

- 라벨 없는 지표 비교입니다. 정답 위치가 없어서 어느 보정이 더 정확한지는 그때 몰랐습니다. 첫 열은 기존 `experiments/full_match26` 결과와 숫자가 같습니다.
- ID 수와 사건 수는 따로 보는 지표가 아닙니다. 6분 창이 이어지는 10곳에서 새 ID가 첫 열 20개, HOGEUN 쪽 14개 생기고(12 + 20 = 32, 12 + 14 = 26), 사건 33번 중 27번, 21번 중 17번이 경기 중간에 새로 생긴 ID의 것입니다.
- `summary.json`의 최고 속도는 아직 믿기 어렵습니다. 두 보정 모두 10 m/s가 넘는 값은 전부 6분 창 이음매 하나(17:35, 1055초 근처)에서 나옵니다 (첫 열 20.4 m/s, HOGEUN 쪽 14.3 m/s). 추적이 박스 없이 3초까지 메워 넣은 구간에서도 높은 속도가 나올 수 있습니다 (20:00부터 3분 구간의 8.7 m/s).
- 표의 `calibration/` 열은 60초 화면 한 장으로 만든 예전 보정에 cam1은 2:40 이후 (-5.8, -9.2) px, cam2는 46:13 이후 (+12.2, -1.3) px 옮겨 쓴 결과입니다 (측정 방법은 `src/futsal/nearfar.py`). 11/11부터는 HOGEUN의 경기 전체 시간별 보정을 쓰고, 같은 명령의 결과는 ID 24개, 절반 넘게 / 80% 넘게 보인 ID 7 / 6개, 한가운데서 생기거나 끊긴 ID 17번(분당 0.32), 두 카메라 위치 차 0.83 → 0.184 m입니다 (`experiments/full_match_1111`, 추적 코드도 그사이 바뀌어서 표와 바로 비교하지는 않습니다).
- 첫 열의 카메라 움직임 값(`experiments/full_match.py`의 `KNOCKS`, cam1 2:40 전 (41, 19) px, cam2 46:13 뒤 (13.8, 1.3) px)은 예전 값입니다. 부딪힌 지 1.5초 뒤에 잰 값인데, cam1은 그때 아직 흔들리는 중이었습니다. 흔들림이 멎은 뒤 잰 값(cam1 (5.8, 9.2) px, cam2 (12.2, -1.3) px, `nearfar.POSES_20261008`)과 cam1은 35 px 넘게, cam2는 3 px 정도 다릅니다. 가운데 열은 같은 탭 보정에 새 값을 쓴 결과입니다 (임시 복사본으로 돌림, 저장소 코드는 예전 값 그대로). 움직임 값만 바꿔도 ID가 32개에서 29개로 줄어서, 보정끼리의 차이 중 일부는 이 값 때문입니다.
